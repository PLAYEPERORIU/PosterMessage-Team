## How Can I Contribute?

### Reporting Bugs

If you find a bug or unexpected behavior across any of our 16 projects or official websites:
1. Search our [Issues](https://github.com/PLAYEPERORIU/PosterMessage-Team/issues) to ensure it hasn't already been reported.
2. If not, open a new issue using our **Bug Report** template.
3. Include clear reproduction steps, expected vs. actual behavior, browser/OS version, and screenshots or logs if possible.

### Suggesting Enhancements

We are always looking for fresh ideas to make our tools faster and more intuitive:
1. Open an issue using the **Feature Request** template.
2. Describe the feature, why it is valuable to the community, and any architectural ideas you have for implementation.

### Submitting a New Project

Have you built a tool or service powered by PosterMessage technologies (e.g., PostAPI, PosterMessage Cloud)?
1. Open an issue using the **Project Proposal** template.
2. Provide project name, description, live URL, source repo (if open-source), and relevant tags.
3. Once reviewed by the core team, your project can be featured in our official catalog and website.

### Pull Requests

1. **Fork the repository** and create your branch from `main`:
   ```bash
   git checkout -b feature/your-feature-name
   ```
2. **Make your changes** following our style guides.
3. **Write clear commit messages** adhering to [Conventional Commits](https://www.conventionalcommits.org/).
4. **Push your branch** to your fork:
   ```bash
   git push origin feature/your-feature-name
   ```
5. **Open a Pull Request** against `main` describing your changes and referencing any related issues.

## Commit Message Conventions

We use the [Conventional Commits](https://www.conventionalcommits.org/) specification:

- `feat:` A new feature or project addition
- `fix:` A bug fix or broken link correction
- `docs:` Documentation changes only (e.g., README, guides)
- `style:` Formatting changes that do not affect the meaning of code
- `refactor:` Code refactoring without fixing a bug or adding a feature
- `perf:` Performance improvements
- `chore:` Maintenance tasks, dependency updates, CI workflows

**Example:**
```
feat(postapi): add endpoint latency benchmarks to documentation
fix(links): update domain routing for mini cloud
docs(privileges): clarify contributor tier access quotas
```

## Style Guidelines

- **Markdown:** Use clean GitHub-flavored markdown with consistent header hierarchies (`#`, `##`, `###`).
- **Language:** All primary repository documentation must be written in clear, concise English.
- **Links:** Verify all external links to live domains (`postermessage.freebuff.app`, `space-z.ai`, etc.) before submitting.
